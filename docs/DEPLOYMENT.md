# Deploying to Render

Two Docker services from [`render.yaml`](../render.yaml), plus an external
MySQL. Render has no MySQL offering and this stack is MySQL-specific
(`drizzle-orm/mysql2` on the Node side, `pymysql` on the Python side), so the
database comes from TiDB Cloud Serverless, which is wire-compatible and has a
free tier.

```
                    ┌─────────────────────────────┐
  browser ─────────▶│ eai-api   Node + React SPA  │
                    └──────────┬──────────────────┘
                               │ X-Service-Token
                    ┌──────────▼──────────────────┐
                    │ eai-ml    FastAPI + sklearn │
                    └──────────┬──────────────────┘
                               │ TLS
                    ┌──────────▼──────────────────┐
                    │ TiDB Cloud Serverless MySQL │
                    └─────────────────────────────┘
```

## What free tier actually gives you

Worth reading before you spend an hour on this, because two of these are
surprising:

| | Consequence |
|---|---|
| Suspends after ~15 min idle | First visit after a pause takes 30–60s |
| No persistent disk | The model registry is empty on every wake — hence `MODEL_BUNDLE_URL` below |
| 512 MB RAM | Serving the champion measures ~340 MB, so it fits. **Training does not** — don't press "Load Demo Data"'s training step here, train locally |
| Instance hours pooled across free services | Keeping both warm with an external pinger would exhaust the monthly allowance. Let them sleep |

The API and the ML service sleep **independently**, so the first prediction
after an idle period pays the ML cold start on top. `render.yaml` sets
`ML_HEALTH_TIMEOUT_MS=90000` and `ML_TIMEOUT_MS=120000` for that reason; with
the code defaults (3s / 10s) every such request fails.

This is fine for proving the deploy works and for a link you warn someone
about. It is not a demo that feels instant. To fix properly: `plan: starter`
on `eai-api`, `plan: standard` on `eai-ml`, and a disk on `eai-ml` at
`/app/ml-service/registry` (~$33/mo), which also makes `MODEL_BUNDLE_URL`
unnecessary.

## 1. Create the database (TiDB Cloud)

1. Sign up at <https://tidbcloud.com> and create a **Serverless** cluster.
2. Create a database named `eai` (or anything; match it below).
3. From **Connect**, take the host, port (`4000`), user and password.

Build the DSN. **The `ssl` parameter is required** — TiDB rejects
unencrypted connections, and `mysql2` only enables TLS when the DSN asks:

```
mysql://USER:PASSWORD@gateway01.REGION.prod.aws.tidbcloud.com:4000/eai?ssl={"minVersion":"TLSv1.2","rejectUnauthorized":true}
```

If the password contains `@ : / ? # &`, percent-encode those characters or the
DSN will parse wrongly.

The Python service reads this **same** string: `engine/db_url.py` prefers
`DATABASE_URL` over the `DB_*` vars and rewrites the TLS parameter into the
spelling `pymysql` understands. One DSN for both services — the old
requirement to keep `DATABASE_URL` and `DB_*` in sync is gone.

## 2. Publish the model bundle

The registry pickles are not in git (OPS-2 — they were ~280 MB). With no disk
on free tier, the ML service needs them fetched at start.

A bundle of the v1.17 champion has already been built for you:

- **File:** `eai-models-v1.17.tar.gz` (16 MB compressed, 50 MB extracted)
- **SHA256:** `2ac9c74f87ce7610229fdb9c31fbd9fef1a9c5439d0337d8615fc09cc3900ed4`

Contents: `rf_{10,30,60}d_v1.17.pkl`, the pinned label encoder, clip
thresholds, feature columns, per-horizon feature importance and metadata, and
the drift reference.

Upload it as a **GitHub release asset** (Releases → Draft a new release → tag
`models-v1.17` → attach the file → publish), then copy the asset's download
URL. It must be `https://`; the entrypoint refuses anything else.

> The archive holds pickles, and unpickling executes code. `render.yaml` pins
> `MODEL_BUNDLE_SHA256` so a swapped asset cannot turn a restart into code
> execution. If you rebuild the bundle, update that digest.

To regenerate the bundle later:

```bash
cd ml-service/registry
tar -czf ../../eai-models-v1.17.tar.gz \
  rf_10d_v1.17.pkl rf_30d_v1.17.pkl rf_60d_v1.17.pkl \
  label_encoder_category_v1.17.pkl clip_thresholds_v1.17.json \
  feature_cols_v1.17.json \
  feature_importance_10d_v1.17.json feature_importance_30d_v1.17.json \
  feature_importance_60d_v1.17.json \
  metadata_10d_v1.17.json metadata_30d_v1.17.json metadata_60d_v1.17.json \
  drift_reference_v1.17.json drift_reference.json
sha256sum ../../eai-models-v1.17.tar.gz
```

## 3. Deploy the blueprint

1. Render dashboard → **New** → **Blueprint**.
2. Point it at `craft-b/enterprise-asset-intelligence`, branch `main`.
3. Render reads `render.yaml` and proposes `eai-api`, `eai-ml` and the
   `eai-shared` env group. Apply.

`SESSION_SECRET` and `ML_SERVICE_TOKEN` are generated by Render — you never
choose or see them. The token lives in the shared group precisely so both
services get the *same* value; the ML service's auth middleware is a no-op
when it is blank, which on a public service would leave `/train` and
`/models/promote` open.

The first build takes a while — the ML image compiles scipy/numba wheels.

## 4. Fill in the three dashboard values

Marked `sync: false` in the blueprint, so Render prompts for them. They are
not in git because two carry credentials.

| Service | Variable | Value |
|---|---|---|
| `eai-api` | `DATABASE_URL` | the DSN from step 1 |
| `eai-ml` | `DATABASE_URL` | the same DSN |
| `eai-ml` | `MODEL_BUNDLE_URL` | the release asset URL from step 2 |

Then, once `eai-ml` has a URL, set on `eai-api`:

| Service | Variable | Value |
|---|---|---|
| `eai-api` | `ML_SERVICE_URL` | `https://eai-ml.onrender.com` — the real origin, no trailing slash |

Check the actual hostname on the `eai-ml` page; Render appends a suffix if the
name was taken. A blueprint cannot compose this from another service's host,
which is why it is manual.

## 5. First boot

`eai-api`'s entrypoint applies migrations before starting the server, so the
schema (including the `sessions` table) is created on first deploy. Watch for:

```
[ENTRYPOINT] applying database migrations...
[ENTRYPOINT] migrations up to date
```

A failure here exits non-zero rather than starting against a schema that does
not match — the log names the cause:

```
[BOOT] startup failed: Failed query: ...
  caused by: connect ECONNREFUSED  [ECONNREFUSED]
```

`eai-ml` should report:

```
[ENTRYPOINT] registry is empty — fetching model bundle
[ENTRYPOINT] checksum verified
[ENTRYPOINT] extracted 3 model files
[STARTUP] Champion: v1.17
```

## 6. Seed the demo data

Open `eai-api`'s URL, create the first account, and use **Load Demo Data** on
the onboarding screen.

**Skip or expect failure on the training step.** The seed pipeline's step 7
calls the ML service's `/train`, which will not complete in 512 MB. The model
is already present from the bundle, so you do not need it — the remaining
steps (seed, batch predictions, drift reference) are what you want. If the
pipeline marks itself failed at step 7, the data and the predictions from the
bundled champion are still there.

To get a properly trained model matched to seeded data, train locally against
the same `DATABASE_URL` and re-publish the bundle:

```bash
cd ml-service
python training/train_model_multihorizon.py
```

## Verifying

```bash
curl -s https://eai-api.onrender.com/api/health
# {"status":"healthy","timestamp":"..."}

curl -s https://eai-ml.onrender.com/health
# model_loaded should be true, model_version v1.17

# The token gate — must be 401, never 200:
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://eai-ml.onrender.com/train

# The docs gate - must be 401 or 404, never 200:
for p in /docs /redoc /openapi.json; do
  printf '%-16s %s\n' "$p" "$(curl -s -o /dev/null -w '%{http_code}' "https://eai-ml.onrender.com$p")"
done
```

Those last two are worth repeating after any env change.

A `200` from `/train` means `ML_SERVICE_TOKEN` is not set on `eai-ml`. The auth
middleware is a no-op when that variable is blank, so anyone could retrain or
promote a model.

A `200` from a doc path means `ENABLE_API_DOCS` was turned on, publishing every
path and schema of the service.

## Known gaps on this setup

- **Swagger UI is off.** `ENABLE_API_DOCS` is `"false"` in `render.yaml`, so
  `/docs`, `/redoc` and `/openapi.json` are not registered as routes at all --
  they 404 even for a caller holding the service token. Only `/health` bypasses
  the token check, because platform health checks cannot send one. Set the flag
  to `"true"` only if you want the API browsable by anyone with the URL.
- **The ML service is a public web service.** Render's private services are a
  paid feature, so the token is the only thing in front of it. It is compared
  with `hmac.compare_digest`, and admin verbs are audit-logged with the
  forwarded actor.
- **Sessions survive restarts but not a dropped database.** They are in MySQL
  now (`sessions` table), so a redeploy no longer signs everyone out.
- **No CI gate on deploy.** `autoDeployTrigger: commit` ships whatever lands on
  `main`. The GitHub Actions workflow runs the Python tests but does not block
  the deploy.
